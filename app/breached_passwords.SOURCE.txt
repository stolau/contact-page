Where app/breached_passwords.txt came from, and how to make it again
====================================================================

This is the provenance record for the sibling file app/breached_passwords.txt,
the deny-list app/passwords.py refuses a new admin password against. It is a
separate file rather than a header inside the data file for three reasons, the
first of which is the load-bearing one:

  1. A #-prefixed header would force the loader to filter comments out, and a
     comment filter on a DENY-LIST is silently lossy: a breached password that
     begins with "#" would be dropped and thereby quietly allowed. This pinned
     corpus happens to contain no such entry, but it does contain
     "!@#$%^&*()_+", so the shape is entirely plausible in a later one. With no
     header the loader is set(text.splitlines()) — no filtering, no way to be
     lossy.
  2. With no header, sha256sum of the shipped file IS the pipeline's output
     hash. A header would give the file two hashes, "the file" and "the body",
     and the one a person types would be the wrong one. That single hash is
     what lets the test suite pin the corpus.
  3. The MIT notice below is about twenty lines of legal text. In a header it
     is read once and scrolled past; in a file named after the data file it is
     where a person goes to ask where this came from.

A commit SHA and not a branch name: "master" is a moving ref, so a recipe
naming it is not a recipe. The generated SHA-256 is asserted by the test suite,
so "reproducible" is a claim the gate checks rather than a sentence here.


The exact pipeline
------------------

Verbatim, because a loose description of this filter produces a DIFFERENT file.
Building it the shell way (tr + sort -u) yields the same line count and the same
byte count but different bytes and a different set: tr '[:upper:]' '[:lower:]'
is ASCII-only, so a non-ASCII entry survives uppercase, and sort -u orders by
locale rather than by code point.

    raw = open(SRC, "rb").read()                    # sha256 == e9a88f67...
    lines = raw.decode("utf-8").split("\n")         # strict UTF-8
    if lines and lines[-1] == "":
        lines.pop()
    kept = sorted({line.casefold() for line in lines if len(line) >= 12})
    out = "".join(line + "\n" for line in kept).encode("utf-8")
                                                    # sha256 == 6dcf8401...

Four properties of that pipeline are load-bearing:

  * str.casefold(), not str.lower() and not tr. It must be the SAME fold the
    lookup in app/passwords.py uses, or a non-ASCII entry is unreachable.
  * Length is measured on the raw line, BEFORE folding. Casefolding can lengthen
    a string (ß becomes ss). An entry shorter than 12 raw characters can never
    be reached anyway: app/passwords.py refuses the typed password on length
    before it ever consults this file, so every shorter entry is dead weight.
    That is why the file is 30k entries and not 1M.
  * Nothing is stripped. A breached password may legitimately end in a space,
    and stripping would silently alter entries — worse, it would invite someone
    to strip the TYPED password too, which app/passwords.py must never do.
    (Measured: after the length filter this corpus happens to carry zero
    entries with surrounding whitespace. That is a property of THIS pinned
    corpus, which is exactly why pinning it by checksum is what makes the test
    asserting it stable.)
  * sorted() is code-point order, LF line endings, and a trailing newline on
    the last entry. .gitattributes pins the file to LF so a checkout cannot
    rewrite them.

No generation script is committed. A script nothing in CI ever runs rots
silently; this recipe cannot, because the test suite re-checks the output hash
on every run.


To regenerate it deliberately
-----------------------------

Download the file from a newer SecLists commit, re-run the pipeline above, and
then update ALL of: the commit SHA, both SHA-256 values and both sizes in this
file, and the pinned hash in tests/test_passwords.py. The suite going red is
the point — it is the only signal that the shipped data and this record have
drifted apart.


The honest limitation
---------------------

This is a snapshot, not a corpus. It is roughly thirty thousand common
passwords of twelve characters or more — not the ~850-million-entry Have I Been
Pwned set. It catches the passphrases and padded passwords a person actually
reaches for; it does not and cannot mean "this password has never been
breached". Do not describe the check as breached-password checking without that
qualifier.

It also contains a handful of mojibake entries — 66 non-ASCII lines, several of
them plainly double-encoded upstream. They are valid UTF-8 and harmless as
deny-list entries. Noted here so nobody later finds them and concludes the file
is corrupt.
